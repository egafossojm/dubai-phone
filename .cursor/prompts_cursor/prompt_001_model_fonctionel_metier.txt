Le projet est une application complète de gestion d'un magasin spécialisé dans la vente de :

- smartphones ;
- téléphones mobiles ;
- tablettes ;
- ordinateurs ;
- accessoires ;

ACHAT
→ RÉCEPTION
→ STOCK
→ VENTE
→ PAIEMENT
→ CLIENT
→ GARANTIE / RETOUR

# 6. PRINCIPES MÉTIER FONDAMENTAUX

Le système doit être conçu autour des principes suivants.

## 6.1 Traçabilité

Toute opération importante doit pouvoir être retracée.

Exemples :

- entrée en stock ;
- sortie de stock ;
- vente ;
- paiement ;
- remboursement ;
- retour ;
- ajustement de stock ;
- modification de prix ;
- modification d'une information sensible ;
- création ou modification d'un utilisateur ;
- modification de permissions.

---

## 6.2 Intégrité financière

Les montants financiers doivent être traçables.

Une vente ne doit jamais simplement disparaître.

Une transaction financière importante doit conserver son historique.

Les corrections doivent être réalisées par des opérations compensatoires ou explicitement auditées plutôt que par suppression silencieuse.

---

## 6.3 Intégrité du stock

Le système doit pouvoir expliquer pourquoi le stock actuel possède sa valeur actuelle.

Les mouvements de stock doivent être identifiables par leur origine :

- achat ;
- réception ;
- vente ;
- retour ;
- ajustement ;
- perte ;
- dommage ;
- transfert éventuel ;
- autre événement métier autorisé.

---

## 6.4 Produits sérialisés

Les produits tels que les smartphones, certains ordinateurs et certains équipements électroniques peuvent nécessiter une identification individuelle.

Un produit commercial et un appareil physique doivent être considérés comme deux concepts différents.

Exemple :

PRODUCT
    ↓
Samsung Galaxy S25 256 GB

DEVICE
    ↓
IMEI
Serial Number
IMEI 2 éventuel

Le système doit pouvoir déterminer :

- quel appareil a été acheté ;
- quand il a été reçu ;
- dans quel stock il se trouve ;
- à quel client il a été vendu ;
- quelle vente correspond à cet appareil ;
- quelle garantie lui est associée ;
- s'il a été retourné ;
- quel est son état actuel.

# 9. MODÈLE DE PRODUIT

Définis clairement la différence entre :

### Product

Produit commercial.

Exemple :

Samsung Galaxy S25 256 GB.

### Product Variant

Variation du produit.

Exemple :

Samsung Galaxy S25
- 256 GB
- Noir

### Serialized Device

Unité physique identifiable.

Exemple :

- IMEI 1 ;
- IMEI 2 ;
- Serial Number.

### Stock Item

Représentation de la disponibilité commerciale d'un produit.

Le modèle doit permettre de gérer correctement :

- produits sérialisés ;
- produits non sérialisés.

# 10. MODÈLE DE VENTE

Formalise le modèle suivant :

SALE
    │
    ├── CUSTOMER
    │
    ├── SALE ITEMS
    │      ├── PRODUCT
    │      ├── QUANTITY
    │      ├── UNIT PRICE
    │      ├── DISCOUNT
    │      └── SERIALIZED DEVICE éventuel
    │
    ├── PAYMENT(S)
    │
    ├── CREDIT ACCOUNT éventuel
    │
    ├── STOCK MOVEMENTS
    │
    └── RECEIPT

Une vente doit pouvoir contenir plusieurs lignes.

Une vente doit pouvoir contenir plusieurs paiements si le modèle métier l'autorise.

Exemple :

Total :
600 000 FCFA

Paiements :

200 000 FCFA CASH
150 000 FCFA ORANGE MONEY
250 000 FCFA MTN MOBILE MONEY

Le modèle doit pouvoir représenter cette situation.

# 11. PAIEMENTS

Modélise explicitement les méthodes :

- CASH ;
- ORANGE_MONEY ;
- MTN_MOBILE_MONEY ;
- INSTALLMENT.

Ne considère pas INSTALLMENT comme une simple méthode de paiement physique.

Il s'agit d'un mécanisme de financement / crédit associé à une vente.

Documente la différence entre :

PAYMENT METHOD

et

PAYMENT TRANSACTION

et

INSTALLMENT / CREDIT ACCOUNT

et

INSTALLMENT PAYMENT.

# 15. RETOURS

Formalise le workflow :

REQUESTED
    ↓
INSPECTING
    ↓
ACCEPTED / REJECTED

Si ACCEPTED :

ACCEPTED
    ↓
REFUND / EXCHANGE / STORE_CREDIT
    ↓
COMPLETED

Définis également les effets potentiels sur :

- stock ;
- paiement ;
- vente ;
- crédit ;
- garantie ;
- appareil sérialisé ;
- historique client.

- un client ;
- un produit ;
- un appareil sérialisé ;
- une période de validité.

Workflow recommandé :

ACTIVE
    ↓
CLAIMED
    ↓
INSPECTING
    ↓
RESOLVED

ou :

ACTIVE
    ↓
EXPIRED

Définis les règles permettant de déterminer si une garantie est valide.

# 26. CAS LIMITES

Identifie explicitement les cas limites.

Au minimum :

### Vente

- stock insuffisant ;
- produit désactivé ;
- appareil déjà vendu ;
- IMEI inexistant ;
- paiement incomplet ;
- paiement supérieur au montant dû ;
- annulation ;
- remise excessive.

### Stock

- stock négatif ;
- doublon IMEI ;
- appareil inconnu ;
- mauvais emplacement éventuel ;
- ajustement ;
- produit endommagé.

### Crédit

- échéance dépassée ;
- paiement partiel ;
- paiement supérieur au solde ;
- paiement annulé ;
- crédit entièrement payé ;
- client ayant plusieurs crédits.

### Retour

- retour hors délai ;
- produit endommagé ;
- IMEI différent ;
- produit déjà retourné ;
- remboursement partiel ;
- échange.

### Achat

- réception partielle ;
- quantité reçue supérieure à la quantité commandée ;
- produit manquant ;
- IMEI dupliqué ;
- commande annulée après réception partielle.
